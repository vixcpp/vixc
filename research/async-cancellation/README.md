# Async and Cancellation Research

This directory contains research for possible VixC language semantics around asynchronous computation, suspension, structured lifetime, and cancellation.

The goal is not to introduce another task library, executor, event loop, or coroutine wrapper.

C++ already provides several mechanisms for asynchronous and concurrent programming:

- threads
- futures
- promises
- callbacks
- coroutines
- executors in external libraries
- event loops
- task systems
- synchronization primitives
- platform-specific asynchronous I/O

The research question is different:

> Can VixC provide a coherent semantic model for asynchronous computation and cancellation without requiring one runtime, one scheduler, or one library representation?

This work is exploratory.

No async or cancellation syntax described here should be considered stable.

## Motivation

Asynchronous C++ is not limited by an inability to start work concurrently.

The ecosystem already contains many ways to do that.

The difficulty appears when several questions must be answered together:

- When does an asynchronous computation begin?
- What owns it?
- How long may it outlive the scope that created it?
- How is its successful value obtained?
- How is recoverable Failure represented?
- How is cancellation requested?
- When does cancellation become observable?
- What must be cleaned up before completion?
- Can abandoned work continue silently?
- Which scheduler executes continuation code?
- What happens if a parent computation stops before its children?
- How are exceptions related to asynchronous Failure?
- Does destruction wait for unfinished work?
- Can asynchronous work escape into global lifetime accidentally?

Different C++ libraries answer these questions differently.

VixC research is interested in whether some of these properties should become explicit semantic information rather than remaining distributed across task types and library conventions.

## Async is not a scheduler

The first important distinction is between asynchronous semantics and scheduling policy.

A language can understand that a computation may suspend without deciding:

- which thread executes it
- whether a thread pool exists
- whether an event loop is used
- whether I/O uses `epoll`, `io_uring`, IOCP, kqueue, or another mechanism
- whether execution is single-threaded
- whether work migrates between threads

These are related implementation concerns, but they are not the same as the semantic meaning of an asynchronous computation.

VixC should avoid defining:

```text
async = run on another thread
```

because suspension and concurrency are different concepts.

An asynchronous operation may execute entirely on one thread while yielding control during I/O.

Likewise, a computation can run concurrently without using an async language model.

## Async is not parallelism

Parallelism means multiple computations execute at the same time.

Asynchrony means a computation can make progress without requiring one caller to block until completion.

These properties can overlap, but neither implies the other.

For example, an event loop may execute thousands of asynchronous operations on one thread.

A parallel numerical algorithm may use many threads while remaining completely synchronous from the caller's perspective.

VixC should preserve this distinction.

A future async feature should describe computation behavior rather than promise parallel execution.

## Async is not a thread abstraction

A VixC async computation should not necessarily correspond to:

```cpp
std::thread
```

A thread has operating-system and scheduling properties that are too specific to represent every asynchronous computation.

An asynchronous operation may instead correspond to:

- a coroutine frame
- an I/O request
- an event-loop task
- a continuation chain
- a remote operation
- a platform task
- a library-specific future
- a state machine generated by the compiler

The source-level semantic model should remain independent from those representations.

## Cancellation is not Failure

Cancellation is one of the main reasons this research is separated from Failure.

The current Outcome hypothesis distinguishes:

```text
success
none
failure
stopped
```

Recoverable Failure means a computation completed unsuccessfully because a declared recoverable problem occurred.

Cancellation is different.

A cancelled computation may have done nothing wrong.

The caller may simply no longer require the result.

For example:

```text
download started
user navigated away
download no longer needed
operation stops
```

Treating this as:

```text
failure(CancelledError)
```

is possible as a library convention, but it loses an important semantic distinction.

VixC research therefore uses `stopped` as a separate working outcome category for intentional interruption.

## Stopped is provisional terminology

The word:

```text
stopped
```

is currently semantic research vocabulary.

It is not committed language syntax.

The concept is intended to represent computation that does not reach normal success or recoverable Failure because execution was intentionally ended.

Potential causes may include:

- cancellation
- parent scope termination
- explicit stop request
- timeout policy
- race resolution where another branch completed first

Whether all of these should share one Outcome state is still an open question.

The research should not turn the provisional name into specification prematurely.

## Cancellation request and cancellation completion are different

A cancellation request does not necessarily mean the target computation has already stopped.

This distinction is fundamental.

Conceptually:

```text
request cancellation
```

means:

> The caller no longer wants this computation to continue if it can stop safely.

The computation may still need to:

- observe the request
- finish an indivisible operation
- release resources
- unregister callbacks
- complete cleanup
- restore invariants
- notify dependent computations

Only after that can the computation become:

```text
stopped
```

The language should not equate a request with completed cancellation unless its model explicitly guarantees immediate interruption.

## Cooperative cancellation

The likely starting point for VixC research is cooperative cancellation.

In a cooperative model, a computation reaches defined points where cancellation can be observed safely.

This avoids arbitrary interruption in the middle of operations that may leave state inconsistent.

For example:

```text
begin database update
perform indivisible commit
observe cancellation after commit
```

may be safer than terminating the computation at an arbitrary machine instruction.

Cooperative cancellation also aligns with RAII and structured cleanup.

The exact observation mechanism remains open.

## Forced cancellation

Forced termination is fundamentally more dangerous.

Stopping a computation at an arbitrary point can interrupt:

- mutex ownership
- transaction updates
- object invariants
- allocator state
- external protocol operations
- file writes
- resource initialization

A general language-level cancellation mechanism should not promise safe forced termination unless it can preserve those invariants.

The first VixC model should therefore avoid assuming that cancellation behaves like killing a thread.

## Structured concurrency

One major research direction is structured concurrency.

The central idea is that the lifetime of child computations should be related structurally to the scope that creates them.

Conceptually:

```text
enter scope
start child A
start child B
wait, cancel, or resolve children
leave scope only when child lifetime is resolved
```

The objective is to prevent detached work from silently outliving the state it depends on.

This is particularly relevant to C++ because object lifetime and resource ownership are already central language properties.

## Why unstructured async is difficult

Consider a function that starts work and returns immediately:

```cpp
void start_work()
{
    launch_async_operation();
}
```

If the launched operation captures references to local or external state, several questions appear.

Who owns the operation after `start_work()` returns?

Can the referenced state be destroyed?

Who observes its Failure?

Who cancels it?

Who waits for cleanup?

What happens during application shutdown?

An unstructured task API may answer these questions through documentation or library-specific conventions.

VixC research should investigate whether computation lifetime can become more explicit semantically.

## Parent and child computations

A structured model may introduce a parent-child relationship.

If computation A starts computation B within a structured async scope, B becomes a child of A.

That relationship may imply rules such as:

- A cannot complete while an unresolved child remains
- cancellation of A is propagated to B
- B's Failure must be handled, propagated, or otherwise accounted for
- resources captured by B remain valid for B's lifetime
- leaving the scope resolves every child

These are possible semantic rules, not current specification.

The exact contract needs experiments.

## Detached work

There are legitimate cases for work that intentionally outlives its creator.

Examples include:

- long-running server tasks
- background maintenance
- process-wide telemetry
- daemon-like services
- event dispatch loops

A structured model should therefore not necessarily prohibit detachment.

Instead, detachment may need to be explicit because it changes ownership and lifetime responsibility.

An important research question is:

> Should unstructured lifetime require an explicit source-level operation?

Making detachment visible could prevent accidental task leaks while preserving legitimate background work.

## Async computation as an outcome-producing computation

A future VixC async computation should probably retain the same Outcome vocabulary used by synchronous computation.

Conceptually:

```text
async computation
    success(T)
    failure(E)
    stopped
```

Potentially:

```text
none
```

may also participate when absence is meaningful.

This suggests that async should not invent a separate error model.

Instead, asynchrony describes when a computation completes, while Outcome describes how it completes.

That separation could allow Failure semantics to remain coherent between synchronous and asynchronous code.

## Invocation and eventual completion

Asynchronous functions create an important semantic distinction.

Consider a hypothetical operation:

```text
load_user()
```

Calling it may create or start a computation whose result appears later.

This means there are at least two moments:

```text
invocation
eventual completion
```

A Failure contract may belong to one or both.

For example, invocation itself might fail synchronously because an argument is invalid or a resource cannot be allocated.

The asynchronous operation might later fail because the network becomes unavailable.

The language must decide what the declared Outcome describes.

A clean model may treat the callable as producing an asynchronous computation whose own Outcome is:

```text
success(User)
failure(NetworkError)
stopped
```

but this remains research.

## Relationship with C++ coroutines

C++20 coroutines provide language-level transformation for suspendable functions.

They do not define one universal task model.

The meaning of a coroutine depends heavily on its promise type.

C++ leaves decisions such as:

- start behavior
- suspension
- return representation
- exception handling
- continuation behavior
- frame ownership

to library-defined coroutine types.

This flexibility is powerful.

It also means that:

```cpp
co_await operation();
```

does not by itself establish one universal async semantic model across C++ libraries.

VixC research should build on coroutine capabilities where useful without assuming the coroutine mechanism itself answers the higher-level semantic questions.

## `co_await` already exists

Any VixC async design must consider existing C++:

```cpp
co_await
```

```cpp
co_return
```

```cpp
co_yield
```

Introducing parallel syntax that duplicates them without adding meaningful semantics would not be justified.

The research question is therefore not:

> Can VixC make `await` shorter?

It is:

> Are there semantic properties around task lifetime, cancellation, Failure, and structured concurrency that existing coroutine syntax does not express uniformly enough?

If the answer is no, VixC should prefer existing C++.

## Awaiting is not necessarily propagation

A future await-like operation may need to deal with several outcomes.

For a computation producing:

```text
success(T)
failure(E)
stopped
```

awaiting completion answers when the result becomes available.

It does not automatically answer what happens to Failure or stopped completion.

Possible models include:

```text
await only waits and materializes Outcome
```

or:

```text
await propagates non-success outcomes
```

or separate operations for waiting and propagation.

This should be resolved together with Failure semantics.

## Relationship with `try`

The current Failure research uses:

```cpp
try operation()
```

as a proposed propagation operation.

If asynchronous computations are introduced, several questions appear.

Could source contain conceptually:

```text
try await operation()
```

or:

```text
await try operation()
```

Should one operation perform both waiting and Failure propagation?

Should `try` also propagate `stopped`?

Would cancellation require another operator?

These questions demonstrate why async should not be designed independently from the Outcome model.

## General Outcome propagation

One possible future direction is that propagation operates on all non-success states.

Conceptually:

```text
success(value)
    -> produce value

failure(error)
    -> propagate failure

stopped
    -> propagate stopped
```

This would make propagation an Outcome operation rather than a Failure-only operation.

The current Failure experiment does not commit to this.

The design must first determine whether automatic propagation of stopped computation is always correct.

## Cancellation boundaries

A computation may need locations where cancellation becomes observable.

Possible cancellation points include:

- awaiting another operation
- explicit polling
- entering a cancellable I/O operation
- yielding to a scheduler
- specific language constructs

The language should define cancellation points clearly if cancellation affects control flow.

Unexpected cancellation at arbitrary source locations would make reasoning about invariants difficult.

## Explicit cancellation checks

One model could require an explicit operation conceptually equivalent to:

```text
check cancellation
```

This makes interruption points visible.

The downside is repeated boilerplate.

Another model could define that specific suspension operations are automatically cancellation points.

Real programs are needed to compare these models.

## Cancellation during synchronous work

A cancellation request may arrive while an async computation is executing synchronous CPU work.

Should the computation stop immediately?

In a cooperative model, likely not.

It may continue until it reaches a cancellation observation point.

This means cancellation latency depends on program structure.

Long-running CPU loops may need explicit checks.

The semantic model should make this behavior predictable.

## Cancellation during I/O

Asynchronous I/O is a more complex case.

An operating system or library may or may not support cancelling an outstanding operation.

Possible situations include:

- cancellation succeeds immediately
- cancellation request is queued
- operation completes before cancellation
- cancellation is unsupported
- external action cannot be undone

VixC cannot promise stronger cancellation semantics than the underlying operation can provide.

The language may therefore need to distinguish cancellation request propagation from cancellation guarantees of a concrete operation.

## Cancellation races

A common race is:

```text
operation completes
cancellation requested
```

at nearly the same time.

The semantic model must define which outcome wins or whether this is implementation-dependent within documented constraints.

Possible policies include:

- completion wins once committed
- cancellation wins if observed before publication
- operation-specific behavior

A durable model needs deterministic observable rules where possible.

## Timeout is not necessarily Failure

A timeout can be modeled in several ways.

It may mean:

```text
failure(TimeoutError)
```

if timeout is considered an operational failure.

It may mean:

```text
stopped
```

if the caller imposed a deadline and intentionally stopped waiting.

These are semantically different.

For example:

```text
remote server failed to respond within protocol deadline
```

may be a domain failure.

By contrast:

```text
caller only wants to wait 50 ms and then continue elsewhere
```

may be cancellation policy.

VixC should not force every timeout into one category.

## Deadlines

A future async model may support deadlines rather than only binary cancellation.

A deadline states that work should no longer continue after some time boundary.

This introduces questions about:

- clock source
- propagation
- nested deadlines
- earlier parent deadlines
- conversion into cancellation
- platform implementation

This is likely library or runtime territory unless strong semantic evidence appears.

The first async experiment should not begin with deadline syntax.

## Cancellation tokens

Existing C++ designs often use token-based cancellation.

Conceptually:

```cpp
operation(stop_token);
```

The caller holds a corresponding source that can request cancellation.

This model has strong properties:

- cancellation capability is explicit
- propagation can be library-controlled
- no global cancellation state is required
- ordinary functions remain usable

VixC should examine whether language-level structured cancellation can build on token-like semantics rather than replacing them.

## `std::stop_token`

Modern C++ provides stop-token facilities associated with cooperative cancellation.

This is relevant evidence.

A VixC language model should understand what standard C++ already provides before introducing another mechanism.

Potential questions include:

- Is `std::stop_token` sufficient as the underlying cancellation capability?
- Can structured scopes propagate tokens automatically?
- Would language-level ownership provide value beyond manual token plumbing?
- Does a language abstraction need to expose the token at all?

The answer may differ between semantic and backend layers.

## Cancellation ownership

Who is allowed to cancel a computation?

Possible models include:

- any holder of a cancellation source
- only the parent computation
- an explicit task owner
- multiple cooperative owners
- runtime policy

This is an ownership question, not merely an API naming issue.

The language should avoid ambient global cancellation where source code cannot identify who controls a computation's lifetime.

## Cancellation propagation

Structured concurrency often propagates cancellation through task hierarchy.

For example:

```text
parent stopped
    -> request stop for children
```

The reverse direction is less obvious.

If one child is stopped, should the parent stop?

Usually not automatically.

If one child fails, should sibling computations be cancelled?

Sometimes yes, especially in all-or-nothing parallel composition.

Sometimes no, especially for independent background operations.

The propagation policy may therefore belong to the structured operation that created the children.

## Joining

A structured task scope may require joining children before leaving.

Joining means resolving their lifetime and completion.

This does not necessarily mean blocking an operating-system thread.

In an async function, joining may itself suspend.

The important semantic property is that parent lifetime does not end while owned children remain unresolved.

## Waiting and joining are not the same as blocking

Source terminology should distinguish semantic waiting from thread blocking.

An async join may suspend the current computation while allowing the executor to run other work.

A blocking wait prevents the current thread from doing other work.

If VixC introduces async semantics, diagnostics and documentation should avoid using these terms interchangeably.

## Fire-and-forget

Fire-and-forget APIs intentionally discard result ownership.

This can be useful but dangerous.

A detached computation can fail after the launching scope is gone.

Questions include:

- Where does its Failure go?
- Who owns its resources?
- What happens during shutdown?
- Can it access destroyed state?
- Is its cancellation capability retained?

A VixC structured model may require explicit detachment to make this responsibility visible.

## Unobserved Failure

An asynchronous task may fail without anyone inspecting the result.

Different ecosystems respond differently:

- ignore it
- terminate
- log it
- store it until task destruction
- rethrow during join
- report through a runtime hook

VixC needs a rule eventually.

A Failure-aware task should not silently discard declared recoverable Failure unless the language explicitly permits that behavior.

This is related to the broader question of ignored Failure outcomes in synchronous code.

## Exception interaction

C++ coroutine libraries often capture exceptions in the coroutine promise and rethrow them when awaited.

VixC Failure should remain distinct from ordinary exceptions unless explicitly bridged.

An async computation could potentially have:

```text
success(T)
failure(E)
stopped
```

while ordinary C++ exceptions remain a separate exceptional mechanism.

The language must decide what happens if an uncaught C++ exception escapes an asynchronous body.

Possible models include:

- preserve it as an ordinary exception delivered by the task
- terminate
- convert through explicit policy
- reject some combinations

This remains open.

## `noexcept`

Async functions complicate `noexcept`.

The immediate invocation of a coroutine may return a task object without executing most of its body.

An exception during eventual execution is therefore different from an exception thrown during initial invocation.

VixC should not assume that ordinary function-level `noexcept` directly describes every eventual task failure.

The interaction requires careful definition.

## RAII and cancellation

Cancellation must preserve C++ object lifetime.

Consider conceptually:

```cpp
async operation()
{
    Resource resource;

    await next_operation();

    use(resource);
}
```

If cancellation becomes observable while waiting for `next_operation()`, the scope must still unwind according to ordinary C++ destruction rules before the computation reaches stopped completion.

The cancellation mechanism must not bypass destructors.

This is a fundamental requirement.

## RAII across suspension

Suspension can extend the lifetime of local objects beyond the active stack frame.

C++ coroutines already represent such state in coroutine frames.

VixC must preserve the same semantic ownership guarantees.

A local object that remains live across suspension must remain valid until its scope ends or the computation is destroyed.

Backend lowering must not accidentally move or destroy it early.

## Cancellation cleanup

Stopping an async computation may require asynchronous cleanup.

For example:

```text
open protocol session
request cancellation
send close message
await acknowledgment
finish cleanup
```

This raises a difficult question:

> Can cancellation handling itself suspend?

If yes, stopped completion may require an asynchronous cleanup phase.

If no, some resources may not be cleanly releasable.

The first model should not assume cleanup is always synchronous.

## Cleanup Failure

Cleanup can itself fail.

Suppose cancellation begins and cleanup encounters an I/O error.

Which outcome should be reported?

Possibilities include:

```text
stopped
failure(CleanupError)
combined information
```

There is no obvious universal answer.

The semantic model may need to distinguish primary completion reason from cleanup diagnostics.

This is a later research problem, but it demonstrates why cancellation should not be reduced to one error code.

## Scope guards and cancellation

Existing C++ scope guards and destructors may already provide much cleanup.

VixC should preserve and leverage RAII rather than introducing parallel cleanup semantics unnecessarily.

Any async cancellation model should work naturally with ordinary automatic objects.

## Resource ownership

Asynchronous work frequently captures resources.

A structured model may help establish that resources outlive all child tasks that use them.

For example:

```text
scope owns socket
child operation borrows socket
scope cannot destroy socket before child is resolved
```

This connects directly to future ownership and lifetime research.

Async semantics should preserve enough structure that such analysis could become possible later.

## Borrowed references across suspension

References across suspension are a major safety concern.

For example, a task may hold:

```cpp
T &
```

to an object owned by another scope.

If the task outlives that scope, the reference becomes invalid.

Structured task lifetime can reduce this class of bug.

VixC should investigate whether child computations can be prevented from escaping the lifetime of borrowed state unless ownership is explicitly transferred.

This may eventually connect async and ownership semantics strongly.

## Async return values

A source-level async computation may conceptually produce:

```text
future success(T)
future failure(E)
future stopped
```

The concrete C++ representation may be a task type.

The language model should not necessarily expose that task type as the semantic definition.

A backend could use different task representations depending on environment.

The frontend should preserve the eventual Outcome contract independently.

## Runtime independence

VixC should not require one universal async runtime merely because it introduces async semantics.

Different applications may already use:

- Asio
- libuv
- custom event loops
- platform I/O completion
- game-engine schedulers
- embedded loops
- thread pools
- coroutine libraries

A language model that requires one scheduler would significantly narrow interoperability.

The preferred research direction is to separate semantic operations from runtime execution policy.

## Runtime adapters

One possibility is that VixC eventually defines semantic protocols that runtimes can implement.

For example, an async backend may need capabilities conceptually equivalent to:

```text
schedule continuation
register cancellation
resume computation
destroy computation
```

A runtime adapter could provide those operations.

This is only a research possibility.

Such a protocol should not be designed before concrete experiments show that multiple runtimes can usefully share it.

## Executor questions

If execution policy is external, the frontend still needs to know where an asynchronous continuation runs.

Possible models include:

- inherited executor
- explicit executor parameter
- task-bound executor
- ambient runtime context
- operation-specific scheduler

Executor semantics affect thread affinity and safety.

For example, GUI or event-loop code may require continuation on one specific thread.

VixC should avoid silently migrating execution unless the programming model makes that possibility clear.

## Scheduler affinity

Some computations must resume on a particular scheduler.

Examples include:

- UI threads
- game loops
- network event loops
- actor runtimes

Other computations may be freely scheduled.

A general async model may eventually need semantic information about execution context.

That is likely beyond the first experiment.

## Async functions and ordinary callers

Ordinary C++ code must eventually be able to call a VixC async function.

That requires a concrete representation.

For example, generated C++ may expose a task-like return type.

Questions include:

- Is that type public?
- Can ordinary C++ await it?
- Can it be polled?
- How is cancellation requested?
- Who destroys it?
- Is it ABI-stable?

These questions make interoperability a first-class requirement.

## Calling ordinary async C++ from VixC

The reverse direction is equally important.

Existing libraries already expose:

```cpp
std::future<T>
```

coroutine awaitables, callback APIs, or custom task types.

VixC should not require rewriting them all.

Possible integration strategies include:

- direct support for awaitable C++ types
- adapter protocols
- explicit wrappers
- library-specific integrations

The first experiments should focus on existing C++ async types before introducing a large new standard library.

## Awaitable protocols

C++ coroutines already have an awaitable protocol.

A type can participate through operations related to:

```text
await_ready
await_suspend
await_resume
```

VixC may be able to reuse this existing mechanism for waiting.

That still leaves higher-level questions around:

- Failure
- stopped completion
- cancellation ownership
- structured child lifetime

The language should add only the semantics that are missing.

## Callbacks

Many existing libraries expose callbacks instead of awaitables.

For example:

```cpp
read_async(
    buffer,
    callback);
```

VixC integration may eventually need adapters that turn callback completion into an async computation.

This adaptation has lifetime and cancellation implications.

The language should not hide such conversions if they alter ownership or cancellation guarantees.

## Futures

`std::future` provides eventual value delivery and exception transport.

Its model differs from many coroutine tasks.

Questions include:

- whether waiting blocks
- whether cancellation exists
- when execution starts
- whether results are shared
- how exceptions are transported

VixC should not assume every future-like type provides equivalent async semantics.

## Lazy and eager execution

An asynchronous task may begin:

```text
immediately when created
```

or:

```text
only when awaited or scheduled
```

This distinction affects side effects and lifetime.

For example:

```text
task = operation()
```

may or may not have started `operation`.

The language must eventually make execution start behavior predictable.

If the source-level semantics leave this entirely to backend task types, programs may behave differently across runtimes.

## Start semantics

Potential models include:

- async function invocation starts immediately
- async invocation creates a lazy computation
- explicit start operation
- runtime-defined behavior exposed through the task type

Each has tradeoffs.

Immediate start is easy to understand but may create work before ownership is fully established.

Lazy start can compose well but makes invocation less direct.

Experiments are required.

## Multiple awaits

Can one asynchronous computation be awaited more than once?

Some task types are single-consumer.

Others support shared observation.

This affects:

- ownership of the result
- move-only values
- cancellation
- task state lifetime

The semantic model should not accidentally promise multi-await behavior just because one backend supports it.

## Task ownership

A task handle may represent ownership of an in-progress computation.

Potential models include:

```text
unique task ownership
shared task observation
borrowed task reference
```

This is closely related to the broader VixC ownership research.

The first async model should probably prefer one clear ownership model rather than support every possibility immediately.

## Dropping a task

What happens when a task handle is destroyed before completion?

Possible semantics include:

- request cancellation and wait for cleanup
- request cancellation without waiting
- detach automatically
- block until completion
- destroy only if task has never started
- declare source invalid

Automatic detachment is simple but can create hidden lifetime bugs.

Blocking destruction can be surprising and expensive.

Structured ownership may provide a better answer.

This is one of the most important questions the research must resolve.

## Parent completion

Can a parent async computation return successfully while an owned child is still running?

A strict structured model would say no.

The child must first:

```text
complete
fail
stop
or be explicitly detached
```

This property prevents child work from silently escaping parent lifetime.

It also creates predictable shutdown behavior.

## Failure among siblings

Suppose a scope runs three child operations concurrently.

If one fails, possible policies include:

- wait for the other two
- cancel the other two
- propagate immediately while cleanup resolves children
- collect all outcomes
- let the programmer choose

There is no single correct policy for every use case.

The concurrency construct creating the tasks may therefore need to encode the policy.

For example, a future operation conceptually equivalent to:

```text
all
race
collect
```

may define different sibling behavior.

## `all`

An `all` style operation could mean:

```text
start several computations
succeed when all succeed
if one fails, apply defined Failure policy
if one stops, apply defined stopped policy
```

Questions include ordering of results and failure selection.

This is a library or future language-composition question.

It should not be embedded into the basic meaning of async itself.

## `race`

A `race` style operation completes based on whichever computation resolves first according to defined rules.

The remaining computations may need cancellation.

This is a strong example of why stopped completion is useful.

The losing operations did not necessarily fail.

They may simply be no longer required.

## Determinism

Concurrent scheduling can be nondeterministic.

VixC cannot make all asynchronous programs deterministic.

However, language-level semantics should still define deterministic rules where source behavior should not depend on arbitrary implementation details.

For example:

- object destruction order
- cancellation ownership
- which children must be resolved before scope exit
- whether an operand is evaluated once
- whether a task begins immediately

These rules should not vary accidentally between backends.

## Data races

Async language support does not automatically solve C++ data races.

If multiple computations access shared memory without synchronization, ordinary C++ concurrency rules still apply.

VixC should not imply memory safety merely because work is represented as structured tasks.

Future ownership research may help prevent some categories of shared-state misuse, but that is separate work.

## Memory model

VixC should preserve the C++ memory model unless it intentionally introduces stronger semantics.

Scheduling a continuation across threads may introduce synchronization requirements.

The backend or runtime must ensure that task state is published safely according to the execution model.

These are implementation requirements that can affect semantic guarantees.

## Thread affinity and references

A reference may be valid in lifetime terms but unsafe to use from another thread.

Therefore, ownership alone does not solve async safety.

A future model may need to distinguish:

- lifetime validity
- thread safety
- scheduler affinity

The first async experiment should not claim stronger guarantees than it can enforce.

## Cancellation and locks

Cancellation while holding a lock is dangerous if cleanup logic is not defined.

A cooperative model can reduce this risk because cancellation only becomes observable at known points.

For example, the language may avoid implicit cancellation checks between arbitrary statements.

This gives programmers a chance to maintain invariants around critical sections.

## Cancellation shielding

Some regions may need to complete even after cancellation is requested.

Examples include:

- transaction commit or rollback
- releasing a protocol lease
- writing critical metadata
- restoring an invariant

A future model may need a way to defer cancellation temporarily.

This is sometimes called cancellation shielding or masking in other systems.

No VixC syntax is proposed yet.

The semantic need should be tested first.

## Cleanup scopes

A structured model may need explicit cleanup semantics when cancellation occurs.

However, C++ already provides destructors.

VixC should first determine how far RAII can solve the problem before adding another cleanup construct.

Asynchronous cleanup remains the major case where destructors alone may be insufficient because destructors cannot generally suspend.

## Asynchronous destruction

C++ destructors cannot normally suspend.

This creates tension for resources requiring async cleanup.

Possible patterns include:

- explicit `close()` before destruction
- async scope finalization
- task-owned cleanup operations
- runtime-managed resources

VixC should not attempt to make destructors implicitly asynchronous without extremely strong evidence.

That would conflict deeply with C++ object lifetime semantics.

## Cancellation and destructors

A destructor may run because a computation is leaving a scope due to stopped completion.

The destructor itself follows ordinary C++ semantics.

If it throws during stack unwinding or generated cleanup, normal C++ exception rules remain relevant.

The async model should not silently reinterpret destructor exceptions as cancellation.

## Failure during cancellation

Suppose:

```text
cancellation requested
cleanup begins
cleanup fails
```

The language needs a policy eventually.

One possible approach is that stopped remains the primary outcome while cleanup Failure is diagnostic metadata.

Another is that Failure replaces stopped.

Another is to preserve both.

No stable answer exists yet.

This should be tested with real resource-management scenarios.

## Cancellation reason

Should stopped completion carry a reason?

For example:

```text
user_cancelled
deadline_reached
parent_stopped
race_lost
shutdown
```

If every stopped state carries an arbitrary error value, stopped may become indistinguishable from Failure.

If no reason is available, debugging may become difficult.

A possible model could keep stopped semantically distinct while attaching optional metadata.

This remains open.

## Cancellation source visibility

Should function signatures declare that cancellation is possible?

If every asynchronous computation can be stopped structurally, perhaps it is implicit.

If only some operations are cancellable, the distinction may matter.

The language must decide whether cancellation capability belongs to:

- the async computation type
- the calling context
- the runtime
- explicit parameters

No decision exists yet.

## Async and function type identity

A future async declaration may change callable type and ABI.

Questions include:

- Is async part of function type identity?
- Can an async function override a synchronous virtual function?
- Can it convert to an ordinary function pointer?
- How are callbacks typed?
- Is eventual Outcome part of the callable's type?

These questions must be answered before async syntax becomes stable.

## Failure contracts on async functions

Suppose a future source form conceptually declares:

```text
async User load_user() fails LoadError
```

Does `fails LoadError` describe eventual completion?

That is the likely useful interpretation.

Then the computation could eventually complete with:

```text
success(User)
failure(LoadError)
stopped
```

This model may unify synchronous and asynchronous Failure semantics cleanly.

It still requires a concrete task representation in generated C++.

## Synchronous Failure during task creation

An async call might still fail before the asynchronous computation exists.

Examples include allocation failure or invalid runtime state.

Should that be:

- an ordinary C++ exception
- a separate synchronous Failure
- part of the same task Outcome
- impossible by language contract

The answer depends heavily on task creation semantics.

The first experiment should avoid claiming that every implementation failure is part of the async Outcome.

## Async functions without Failure

An async computation may still only have:

```text
success(T)
stopped
```

if it does not declare recoverable Failure.

This reinforces the idea that async and Failure are separate semantic dimensions.

Likewise, a synchronous function may have:

```text
success(T)
failure(E)
```

without any stopped state if cancellation is not applicable.

## Does every async computation permit stopped?

If cancellation is structurally available, perhaps yes.

But some operations may be non-cancellable once started.

A distinction may be needed between:

```text
cancellation requested
```

and:

```text
computation semantically supports stopped completion
```

An uncancellable operation inside a cancellable parent may need to finish before the parent can stop.

This is common in real systems.

## Cancellation latency

A structured model should not promise instant cancellation.

Instead, programs may need to understand cancellation latency as the time until the next safe observation point.

This is especially relevant for:

- CPU-bound loops
- blocking foreign APIs
- system calls without cancellation
- critical sections

Tooling might eventually help identify long regions without cancellation points, but that is beyond the first experiment.

## Blocking operations inside async code

A blocking operation can stall the executor thread.

VixC may eventually diagnose or annotate such operations if execution context is known.

However, detecting every blocking C++ call is difficult.

The first async model should not require whole-ecosystem blocking analysis.

Runtime and library conventions may remain necessary.

## Foreign functions

Existing C and C++ APIs may block, spawn threads, or use callbacks.

VixC async semantics must interoperate with them.

Adapters should make semantic differences explicit where necessary.

For example, wrapping a blocking function in a thread pool changes scheduling and cancellation properties.

That should not happen invisibly unless a clear runtime policy guarantees it.

## Backpressure

Asynchronous systems often require backpressure.

A producer may generate work faster than a consumer can process it.

This is more relevant to streams and channels than individual tasks.

The first async research should avoid conflating:

```text
single asynchronous computation
```

with:

```text
asynchronous stream
```

Streams may become a separate research area if required.

## Async streams

A stream can produce multiple values over time rather than one eventual Outcome.

Its semantics differ from a task.

Possible outcomes include:

```text
next value
end of stream
failure
stopped
```

This naturally intersects `none` or completion semantics.

VixC should not attempt to force streams into the first task model.

## Generators

C++ coroutines also support generator-like behavior.

Yielding multiple values is not the same as asynchronous task completion.

Any future `yield` research should remain separate from basic async and cancellation semantics.

## Structured scope syntax

No source syntax for structured async scopes has been selected.

Conceptual examples might involve operations such as:

```text
start child
await child
cancel child
join scope
detach child
```

These are semantic operations, not proposed keywords.

The research should determine the minimum necessary source surface after testing library-level approaches.

## Could existing C++ APIs be enough?

This is a central question.

It may be possible for VixC to provide no new async syntax at all.

Perhaps VixC only needs semantic understanding of existing C++ coroutine and task patterns for diagnostics and structured lifetime checking.

Alternatively, a small amount of syntax may significantly improve coherence.

The research should test both possibilities.

## Library-first experiment

Before defining language syntax, an initial experiment could use an ordinary C++ task API and ask whether the frontend can reason about:

- task ownership
- parent-child lifetime
- cancellation propagation
- eventual Failure
- stopped completion

If semantic benefits can be achieved without new syntax, that would reduce language surface.

If they cannot, the missing information will identify what syntax or metadata is actually required.

## Semantic IR

If async becomes a VixC feature, the IR should represent semantic operations independently from runtime implementation.

Possible concepts include:

```text
AsyncComputation
Suspend
Resume
Await
StartChild
Join
RequestStop
Stopped
Detach
```

These names are provisional.

The important point is that the IR should describe meaning rather than generated coroutine helper code.

## Control-flow IR

Async is another strong reason VixC may eventually need a more explicit control-flow IR.

Suspension divides a computation into continuation segments.

Cancellation introduces additional exits.

Failure adds another completion path.

A semantic control-flow representation may need to model:

```text
normal continuation
suspension
success completion
failure completion
stopped completion
```

This should be designed carefully so the IR does not become tied to one coroutine ABI.

## Coroutine lowering

A C++ backend may be able to lower VixC async semantics into C++20 coroutines.

That would provide a native and standard mechanism for suspension.

The backend could generate:

```cpp
co_await
```

and:

```cpp
co_return
```

where appropriate.

However, this strategy still requires a task type, promise type, cancellation integration, and completion representation.

Using coroutines solves transformation mechanics, not the entire semantic model.

## Manual state-machine lowering

Another possible backend strategy is generating an explicit state machine.

This could avoid reliance on C++ coroutine ABI details and provide more control.

It would also be significantly more complex.

Potential costs include:

- generated code size
- manual lifetime management
- more backend implementation
- difficult debugging
- source-map complexity

This strategy should only be considered if C++ coroutines cannot satisfy required semantics.

## Native runtime integration

Some environments may prefer direct integration with their own runtime.

For example:

- an event-driven server runtime
- a game engine
- an embedded scheduler

The semantic frontend should ideally allow multiple backend strategies.

That is another reason to keep async semantics independent from one scheduler or task class.

## Source provenance

Async lowering can generate substantial code from a small source construct.

For example, one await point may correspond to:

- state storage
- suspension check
- continuation registration
- resume logic
- cancellation check
- Failure handling

Generated diagnostics must remain connected to the original source.

Source mapping is therefore particularly important for async code.

## Debugging

Asynchronous debugging is difficult even without source transformation.

A VixC async model should eventually consider:

- stack traces across suspension
- task identity
- parent-child relationships
- cancellation reason
- Failure provenance
- current suspension point

These capabilities may require runtime metadata.

They should not automatically become semantic requirements for the first implementation.

## Task identity

Should every asynchronous computation have a runtime identity?

For debugging, task IDs are useful.

For semantics, they may be unnecessary.

Requiring dynamic identity could impose overhead on every task.

The language should not require it unless needed for observable behavior.

A runtime may provide optional debug identity.

## Diagnostics

Potential async semantic diagnostics include:

```text
owned task escapes its scope
task result is discarded
task is detached implicitly
await outside an asynchronous computation
cancellation operation outside a cancellable context
child task remains unresolved at scope exit
invalid use after task completion
multiple consumption of a single-consumer task
```

These diagnostics depend on the final ownership model.

They should be expressed in source-level terms rather than generated coroutine machinery.

## Await outside async context

If VixC introduces a dedicated await semantic operation, using it in a computation that cannot suspend should produce a frontend diagnostic.

For example, conceptually:

```text
error: this computation cannot suspend
```

The exact source syntax is not yet defined.

The semantic requirement is clearer than the spelling.

## Unresolved child at scope exit

A structured concurrency model could diagnose:

```text
child computation may outlive the scope that owns it
```

unless the child was:

```text
joined
stopped
completed
detached explicitly
```

This would provide stronger lifetime guarantees than many existing task APIs.

It also requires control-flow analysis.

## Implicit detach diagnostics

If a task handle is discarded accidentally, VixC may be able to diagnose it.

For example:

```text
start operation
discard handle
```

may indicate unintended fire-and-forget execution.

Whether this is an Error or Warning depends on the ownership model.

An explicit detach operation could make intent unambiguous.

## Cancellation diagnostics

Potential cancellation diagnostics include:

```text
cancellation requested for a computation that is not owned here
```

or:

```text
stopped outcome is not handled
```

or:

```text
operation cannot observe cancellation before this blocking boundary
```

The last example may require library metadata not available initially.

## Tooling

Async semantics can provide useful information to editors and analysis tools.

Potential tooling includes:

- show child task hierarchy
- show possible suspension points
- show cancellation boundaries
- show eventual Outcome
- show task ownership
- identify detached computations
- visualize propagation of Failure and stopped completion

This would be difficult if async remains only a collection of unrelated library conventions.

## Templates

Async semantics must eventually work with templates.

Questions include:

- Can a template be async depending on a type?
- Can awaitability be constrained by concepts?
- Can eventual Outcome types depend on template parameters?
- When is cancellation capability known?
- Can generic code preserve task ownership?

C++ already provides coroutine customization through types, which may help.

VixC should not replace that generic power unnecessarily.

## Concepts

Existing C++ concepts can express properties of awaitable and task-like types.

A future VixC integration layer may expose concepts for:

```text
awaitable
cancellable
failure-aware computation
structured child
```

Whether these become language-level semantic categories or library concepts remains open.

## Virtual functions

Async virtual methods introduce ABI and lifetime questions.

For example, a virtual method may return a task-like object.

Ordinary C++ can already express this using a concrete task type.

If VixC async syntax hides that representation, generated declarations must remain consistent across overrides.

This is another reason async function type identity must be understood before stabilization.

## Function pointers and callbacks

A hidden async function representation may not convert directly to ordinary:

```cpp
T (*)()
```

Function pointers, callback registries, and C APIs require concrete types.

VixC must preserve interoperability through generated C++ signatures or explicit adapters.

## Exceptions disabled

A strong async model should ideally remain usable in C++ environments compiled without exception support.

If Failure is value-based and async completion is explicit, this may be possible.

A backend task implementation should not require exceptions unless selected by configuration or runtime policy.

This should be part of backend evaluation.

## RTTI disabled

Async semantics should not inherently require RTTI.

Task state and Outcome dispatch can normally be represented statically.

Backends should avoid introducing unnecessary runtime type dependencies.

## Allocation

C++ coroutine frames may allocate dynamically depending on compiler and promise design.

Some environments require allocation-free async behavior.

Questions include:

- Can frames use custom allocation?
- Can frame allocation be elided?
- Can fixed-storage tasks exist?
- Does the language require heap allocation?

The language should not make heap allocation a semantic requirement.

Backend experiments should measure actual behavior.

## Embedded environments

Async semantics may be valuable in embedded systems where threads are expensive or unavailable.

A useful design should therefore consider environments with:

- no exceptions
- no RTTI
- limited allocation
- custom schedulers
- freestanding or near-freestanding C++
- hardware event loops

This strongly argues against coupling async semantics to one heavyweight runtime.

## Performance

Async design must be evaluated using real workloads.

Measurements should include:

- task creation cost
- suspension cost
- resume cost
- cancellation cost
- memory per active task
- generated code size
- allocator behavior
- scheduler overhead
- latency
- throughput

Both fast-path success and cancellation-heavy workloads should be measured.

## Compile time

Coroutine-heavy C++ can increase compilation cost.

Generated task types and templates may also contribute significantly.

VixC should measure:

- native compile time
- template instantiation count
- generated source size
- incremental rebuild behavior

A semantically elegant async model that makes C++ builds dramatically worse may require another representation.

## Zero-cost claims

VixC should avoid claiming async is zero-cost without evidence.

Suspension requires state.

Task ownership requires representation.

Cancellation may require state propagation.

Schedulers have runtime overhead.

The correct objective is transparent and measured cost consistent with the semantics provided.

## First experimental scope

The first async experiment should remain narrow.

A useful initial scope may include:

- one asynchronous computation type
- one successful result
- optional Failure
- cooperative cancellation
- structured parent-child lifetime
- explicit waiting
- no detached tasks by default
- ordinary C++ RAII
- one existing runtime or coroutine backend for experimentation

The experiment does not need to solve:

- distributed tasks
- actors
- async streams
- arbitrary scheduler migration
- every future implementation
- asynchronous destructors
- persistent task graphs

Keeping the first scope narrow will make semantic failures easier to identify.

## Relationship with Failure priority

Async and cancellation should not interrupt completion of the first Failure vertical slice.

Failure currently has concrete frontend work remaining around:

- declaration scope
- semantic IR
- propagation lowering
- C++ emission

Async research should remain compatible with that direction.

In particular, Failure should not be designed in a way that makes eventual async Outcome composition impossible.

## Useful first program

A meaningful async experiment should involve real resource lifetime and cancellation.

For example, conceptually:

```text
load user
    start network operation
    suspend while waiting
    caller cancels
    network operation observes cancellation
    resources are released
    computation completes as stopped
```

A second experiment should involve recoverable Failure:

```text
load user
    network request completes
    server unavailable
    computation completes as failure(NetworkError)
```

These two cases must remain semantically distinct.

## Success criteria

The async research would become promising if experiments demonstrate:

- understandable source-level task lifetime
- predictable parent-child ownership
- cancellation distinct from Failure
- normal RAII cleanup
- no accidental detached work
- interoperability with existing C++ async libraries
- backend independence from one scheduler
- useful diagnostics
- acceptable runtime cost
- acceptable compile-time cost
- clear eventual Outcome semantics

These properties matter more than syntactic novelty.

## Failure criteria

The design should be reconsidered if:

- it requires one mandatory runtime
- it duplicates C++ coroutines without adding meaningful semantics
- structured lifetime cannot coexist naturally with ordinary C++ ownership
- cancellation semantics become too implicit to reason about
- interoperability requires wrapping most existing async libraries
- generated code has unacceptable overhead
- task ownership rules become more complicated than existing library approaches
- source syntax obscures scheduler or lifetime behavior
- async and Failure semantics cannot compose coherently

The research must allow the design to fail.

## What must not become accidental specification

The following remain provisional:

- whether VixC introduces an `async` keyword
- whether VixC introduces an `await` keyword
- whether `co_await` remains the primary syntax
- whether every async computation supports cancellation
- whether stopped is always propagated
- whether cancellation is represented through `std::stop_token`
- whether tasks start eagerly or lazily
- whether dropping a task requests cancellation
- whether child Failure cancels siblings
- whether a task type is supplied by VixC
- whether C++ coroutines are the permanent backend mechanism
- whether async requires runtime support

These are research questions, not commitments.

## Immediate research questions

Before designing syntax, the async work should answer several smaller questions.

First, what semantic information is missing from existing C++ coroutine and task libraries that VixC genuinely needs to own?

Second, can structured parent-child lifetime be represented without introducing a universal runtime?

Third, what is the exact semantic difference between:

```text
failure
```

and:

```text
stopped
```

in real programs?

Fourth, when and how is cancellation observed?

Fifth, what happens when an owned asynchronous computation is abandoned?

Sixth, how are Failure and stopped completion propagated through an asynchronous call chain?

Seventh, can existing C++ awaitable types participate without adapters that destroy their native semantics?

Eighth, what minimum IR is required to represent suspension and completion independently of a scheduler?

These questions should be answered before adding source-level async syntax.

## Research discipline

Async design can become large very quickly.

VixC should distinguish carefully between:

```text
language semantics
task representation
scheduler policy
runtime capability
library convenience
platform behavior
```

These are not the same layer.

For example, the language may require:

```text
owned children cannot escape scope implicitly
```

without requiring:

```text
all children run on the VixC thread pool
```

Likewise, the language may define:

```text
stopped is distinct from failure
```

without defining one universal operating-system cancellation primitive.

Keeping these boundaries clear is necessary if VixC is to remain compatible with the C++ ecosystem.

## Current position

The current working direction is that asynchronous computation should be treated as a computation whose completion may occur later, while Outcome describes how that computation completes.

A future async computation may therefore conceptually complete with:

```text
success(T)
failure(E)
stopped
```

where applicable.

Cancellation is currently modeled as intentional interruption rather than recoverable Failure.

Structured parent-child lifetime is a strong research direction because it may provide meaningful guarantees beyond ordinary task libraries while fitting naturally with C++ ownership and RAII.

No source syntax, task type, scheduler, runtime, or backend representation has been selected.

The next useful evidence should come from small structured-concurrency experiments built on existing C++ mechanisms before VixC commits to a new async language surface.
